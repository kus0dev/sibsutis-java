# Задание 6. Запись на курс с ограничением мест

## Вариант 1: coarse-grained lock

`LockedCourse` хранит `HashSet` студентов, а `enroll` объявлен `synchronized`.
Один монитор защищает и проверку `capacity`, и проверку дубликата, и вставку.
Инвариант простой: `students.size() <= capacity`, студент встречается в set не
более одного раза. Отказ происходит до изменения set, поэтому состояние не
меняется.

Цена: все записи на один курс сериализуются, даже если они могли бы выполняться
параллельно. Для маленького курса это нормально и очень просто.

## Вариант 2: атомарные операции и concurrent collections

`AtomicCourse` использует:

- `ConcurrentHashMap.newKeySet()` — потокобезопасная уникальность студента;
- `AtomicInteger` с CAS — резервирование места без превышения `capacity`.

Сначала поток проверяет, не записан ли студент, затем CAS-циклом резервирует
место. Если после резерва `students.add` сообщает, что студент уже есть,
резерв возвращается через `decrementAndGet`. Если мест нет, отказ происходит
до изменения set.

`available()` считает места по размеру set студентов, поэтому отказ не меняет
наблюдаемое состояние. `reserved` — внутренний счётчик для CAS; во время
параллельных вызовов он может быть больше числа уже добавленных студентов, но
успешных записей всё равно не больше `capacity`.

## Сравнение

| Подход | Плюсы | Минусы |
|---|---|---|
| `synchronized` | Простой, один инвариант и один монитор, легко доказать | Сериализует все записи на курс |
| Atomics + concurrent set | Нет общей блокировки, выше параллелизм | Сложнее: нужен rollback резерва и аккуратная проверка дубликата |

Оба варианта в демонстрации проходят проверки: успешных записей ровно
`capacity`, дубликатов нет, повторная запись отклоняется без изменения
количества занятых мест.
