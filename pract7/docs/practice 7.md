## Задание 1. `Files.readString/writeString`

### Формулировка
Сохраните каталог курсов в UTF-8, прочитайте, обработайте отсутствие файла и существующий каталог вместо файла. Не ловите ошибку только ради печати и продолжения с ложным успехом.

### Алгоритм решения
1. Создать класс `CourseCatalog`, который хранит список `Course` и предоставляет методы сериализации/десериализации в простой текстовый формат.
2. Реализовать `save(Path, CourseCatalog)` с использованием `Files.writeString(..., StandardCharsets.UTF_8)`. Перед записью явно проверить: если путь существует и является каталогом - выбросить `IOException`.
3. Реализовать `load(Path)` с использованием `Files.readString(..., StandardCharsets.UTF_8)`. Проверить существование файла; если путь не существует - бросить `IOException`. Если путь является каталогом - бросить `IOException`. 
4. Продемонстрировать корректную обработку всех трёх случаев (успешное чтение/запись, отсутствующий файл, каталог вместо файла).

### Основные концепты
- `Files.readString`/`Files.writeString` - удобные методы для работы с текстом в кодировке; важно явно указывать `Charset` (здесь `StandardCharsets.UTF_8`).
- Разделение «проверка предусловий» и «действие»: не перехватывать исключения без необходимости, а явно валидировать ситуацию и выбрасывать содержательное исключение.
- Работа с `Path`: `Files.exists`, `Files.isDirectory`, `Files.createDirectories`.

### Важный листинг (фрагмент)
```java
public static void save(Path path, CourseCatalog catalog) throws IOException {
  if (path == null) throw new IllegalArgumentException("path must not be null");
  if (catalog == null) throw new IllegalArgumentException("catalog must not be null");
  if (Files.exists(path) && Files.isDirectory(path)) {
    throw new IOException("path is a directory, not a file: " + path);
  }
  String content = catalog.toText();
  Files.writeString(path, content, StandardCharsets.UTF_8);
}

public static CourseCatalog load(Path path) throws IOException {
  if (path == null) throw new IllegalArgumentException("path must not be null");
  if (!Files.exists(path)) {
    throw new IOException("file does not exist: " + path);
  }
  if (Files.isDirectory(path)) {
    throw new IOException("path is a directory, not a file: " + path);
  }
  String content = Files.readString(path, StandardCharsets.UTF_8);
  return fromText(content);
}
```

### Результат
Реализованы сохранение/чтение каталога в UTF-8, корректная обработка отсутствующего файла и попытки работы с каталогом.

## Задание 2. `Reader`/`Writer`

### Формулировка
Перепишите текстовую обработку через buffered reader/writer, считайте строки и символы. Объясните границу bytes → chars.

### Алгоритм решения
1. Создать `TextProcessor` с методами для работы через `BufferedReader`/`BufferedWriter`.
2. Реализовать подсчёт строк (`readLine()`), подсчёт символов (`read()`).
3. Реализовать копирование текста через `InputStreamReader`/`OutputStreamWriter` в связке с `BufferedReader`/`BufferedWriter`.
4. Продемонстрировать разницу между побайтовым и посимвольным чтением.

### Основные концепты
- **Граница bytes → chars**: байтовые потоки (`InputStream`/`OutputStream`) оперируют байтами. Чтобы получить символы, нужно декодировать байты по определённой кодировке. Класс `InputStreamReader` выполняет преобразование байты→символы по `Charset`. `OutputStreamWriter` выполняет символы→байты. 
- `BufferedReader` добавляет буферизацию и удобные методы (`readLine()`), `BufferedWriter` - буферизацию для записи.
- При работе с текстом всегда предпочтительно использовать символьные потоки и явно задавать кодировку (UTF-8).

### Важный листинг (фрагмент)
```java
// bytes -> chars происходит в InputStreamReader по заданной кодировке
try (BufferedReader br = new BufferedReader(new InputStreamReader(in, StandardCharsets.UTF_8));
     BufferedWriter bw = new BufferedWriter(new OutputStreamWriter(out, StandardCharsets.UTF_8))) {
  String line;
  while ((line = br.readLine()) != null) {
    bw.write(line);
    bw.newLine();
  }
}
```

### Результат
Текстовая обработка реализована через `Reader`/`Writer`, продемонстрированы чтение строк и символов, пояснена граница байты→символы.

## Задание 3. Try-with-resources

### Формулировка
Создайте pipeline чтения и записи, в середине которого возникает исключение. Докажите закрытие обоих ресурсов и правильный порядок close.

### Алгоритм решения
1. Создать классы-ресурсы, реализующие `AutoCloseable`, с логированием в `close()`.
2. В `try-with-resources` открыть два ресурса, вызвать метод, выбрасывающий исключение в середине работы.
3. Перехватить исключение и по выводу убедиться, что оба ресурса закрыты.
4. Проанализировать порядок закрытия - ресурсы закрываются в обратном порядке открытия (LIFO).

### Основные концепты
- `try-with-resources` автоматически вызывает `close()` для всех ресурсов, объявленных в заголовке, даже при возникновении исключения.
- Порядок закрытия обратный порядку создания - это важно, если ресурсы зависят друг от друга.
- Если в блоке `try` и в `close()` выбрасываются исключения, suppressed-исключения добавляются к основному.

### Важный листинг (фрагмент)
```java
try (PipelineResource first = new PipelineResource("first");
     PipelineResource second = new PipelineResource("second")) {
  System.out.println("opened both");
  first.doWork(); // исключение в середине
} catch (Exception e) {
  System.out.println("caught: " + e.getMessage());
}
// Вывод демонстрирует: closing: second, затем closing: first (LIFO)
```

### Результат
Доказано автоматическое закрытие обоих ресурсов и порядок `close()` - последний открытый ресурс закрывается первым.

## Задание 4. Ленивые строки

### Формулировка
Используйте `Files.lines` только внутри try-with-resources. Воспроизведите ошибочный возврат stream наружу и объясните, кто обязан владеть ресурсом.

### Алгоритм решения
1. Реализовать корректный метод `countNonEmpty`, обрабатывающий `Stream<String>` из `Files.lines` строго внутри `try-with-resources`.
2. Реализовать метод `linesLeaked`, возвращающий `Stream<String>` наружу (демонстрационный ошибочный подход).
3. Показать, что при утечке вызывающий обязан закрыть поток, иначе ресурсы (файловый дескриптор) не будут освобождены.

### Основные концепты
- `Files.lines` открывает файловый ресурс и возвращает ленивый `Stream<String>`. Этот `Stream` является ресурсом (`BaseStream` расширяет `AutoCloseable`) - его нужно закрывать.
- Если `Stream` возвращается из метода наружу, ответственность за закрытие неясна - легко забыть вызвать `close()`. Поэтому правильный подход - потребить поток внутри `try-with-resources` и не возвращать его.
- «Кто создаёт ресурс - тот и владеет им» либо ответственность должна быть явно передана вызывающему с обязательным требованием закрытия.

### Важный листинг (фрагмент)
```java
public static long countNonEmpty(Path path) throws IOException {
  try (Stream<String> lines = Files.lines(path, StandardCharsets.UTF_8)) {
    return lines.filter(s -> s != null && !s.isBlank()).count();
  }
  // ресурс закрывается здесь
}

// ошибочный вариант - владелец не определён
public static Stream<String> linesLeaked(Path path) throws IOException {
  return Files.lines(path, StandardCharsets.UTF_8);
}
```

### Результат
Показано корректное использование `Files.lines` внутри `try-with-resources` и проблема возврата потока наружу без передачи владения ресурсом.

## Задание 6. Временный файл и move

### Формулировка
Записывайте новый каталог во временный файл того же каталога, flush/close, затем заменяйте целевой файл move-операцией. Обработайте отсутствие atomic move на файловой системе.

### Алгоритм решения
1. Создать временный файл в том же каталоге, что и целевой (`Files.createTempFile(dir, ...)`).
2. Записать новое содержимое во временный файл. `Files.writeString` выполняет запись и закрывает поток - flush/close обеспечены.
3. Попробовать выполнить атомарную замену через `Files.move` с опциями `REPLACE_EXISTING, ATOMIC_MOVE`.
4. При `AtomicMoveNotSupportedException` выполнить обычный `move/replace` как fallback.
5. Обеспечить удаление временного файла при ошибке.

### Основные концепты
- Запись во временный файл в том же каталоге минимизирует проблемы с разными файловыми системами при замене.
- Атомарный `move` (где поддерживается) предотвращает частично записанный целевой файл для наблюдателей.
- Если атомарный move недоступен - нужно явно обработать ситуацию (fallback), не игнорируя ошибку молча.
- Важно корректно убирать временные файлы при нештатных ситуациях.

### Важный листинг (фрагмент)
```java
Path tmp = Files.createTempFile(dir, "catalog", ".tmp");
try {
  Files.writeString(tmp, content, StandardCharsets.UTF_8);
  try {
    Files.move(tmp, target, StandardCopyOption.REPLACE_EXISTING, StandardCopyOption.ATOMIC_MOVE);
  } catch (AtomicMoveNotSupportedException e) {
    System.out.println("atomic move not supported, using non-atomic replace");
    Files.move(tmp, target, StandardCopyOption.REPLACE_EXISTING);
  }
} catch (Exception e) {
  try { Files.deleteIfExists(tmp); } catch (IOException ignored) {}
  throw e;
}
```

### Результат
Реализована безопасная замена файла через временный файл с обработкой отсутствия атомарного move.

## Задание 9. Версионируемый формат

### Формулировка
Добавьте schema version, checksum и migration из версии 1 в 2. Неизвестная будущая версия не читается как старая. Повреждение обнаруживается до публикации объектов.

### Алгоритм решения
1. Определить формат с заголовком: `magic`, `short version`, `int payloadLength`, `payload`, `checksum` (SHA-256).
2. Сформировать `payload` отдельно, вычислить контрольную сумму по `payload`.
3. При чтении: проверить magic, **если версия > текущей поддерживаемой - бросить исключение (не читать как старую)**.
4. Прочитать payload и checksum, сверить контрольную сумму - при несовпадении бросить исключение **до** десериализации/публикации объектов.
5. Реализовать миграцию v1->v2 (например, добавить поле `capacity` с дефолтным значением).
6. Продемонстрировать чтение v2, миграцию v1->v2, отклонение будущей версии, обнаружение повреждения.

### Основные концепты
- **Версионирование схемы** позволяет эволюционировать формат без поломки совместимости.
- **Checksum** (контрольная целостность) позволяет обнаружить повреждение данных до создания объектов предметной модели.
- **Миграция** преобразует данные старой версии к текущей схеме; важно явно различать поддерживаемые версии.
- Принцип «fail fast» - отказ при неизвестной будущей версии, а не попытка интерпретировать как старую.

### Важный листинг (фрагмент)
```java
short version = in.readShort();
if (version > VERSION_2) throw new IOException("unknown future version: " + version); // не читаем как старую
...
byte[] payload = new byte[payloadLen];
in.readFully(payload);
byte[] given = new byte[32];
in.readFully(given);
byte[] calc = sha256(payload);
if (!MessageDigest.isEqual(calc, given)) throw new IOException("checksum mismatch"); // повреждение до публикации
```

### Результат
Реализован версионируемый формат с checksum, строгой проверкой версий, миграцией v1->v2; повреждение и будущая версия корректно отклоняются.
