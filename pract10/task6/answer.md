# Задание 6. Общий deadline

## Один бюджет на все стадии

Дедлайн вычисляется один раз в монотонном времени:

```java
long deadline = System.nanoTime() + TimeUnit.MILLISECONDS.toNanos(BUDGET_MILLIS);
```

Перед каждой стадией остаток считается заново:

```java
long remaining = deadline - System.nanoTime();
if (remaining <= 0) {
  System.out.println(name + ": skipped, no time left");
  return;
}
```

`System.nanoTime()` не зависит от перевода системных часов и подходит для
измерения интервалов. `System.currentTimeMillis()` для дедлайна опасен: часы
могут прыгнуть назад или вперёд, и бюджет станет отрицательным или бесконечным.

Бюджет не сбрасывается на каждой стадии. Если первая стадия заняла 150 мс из
600, второй стадии достаётся около 450 мс, третьей — около 150 мс. Именно
поэтому четвёртая стадия не запускается вовсе: времени уже нет.

## Отмена и ожидание завершения

`Future.get(remaining, NANOSECONDS)` ограничен остатком общего бюджета. При
`TimeoutException` вызывается `cancel(true)`: поток получает interruption.
Ожидать после этого второй раз тем же `get` нельзя — он либо сразу бросит
`CancellationException`, либо начнёт новое ожидание, которое уже не входит в
исходный бюджет.

`cancel(true)` — только запрос. Чтобы убедиться, что задача действительно
остановилась и освободила ресурсы, используется отдельный `CountDownLatch`,
который отсчитывается в `finally` задачи. На его ожидание выделен небольшой
**новый** бюджет `CANCEL_GRACE_MILLIS`. Это не продолжение старого дедлайна:
стадия уже признана провалившейся, а короткое ожидание нужно только для
корректного завершения.

```text
budget=600ms
load course: done
load modules: done
build report: timeout, cancel(true), stopped=true
send notification: skipped, no time left
total elapsed=603ms
```

Задача `build report` спала 400 мс, но получила только ~150 мс. После
interruption `Thread.sleep` бросил `InterruptedException`, задача восстановила
флаг, вышла из `call` и отсчитала latch. Следующая стадия не стартовала.

## Structured concurrency

В примере всё сделано вручную: один executor, один deadline, явный `cancel` и
явное ожидание. Если стадий и веток станет больше, легко забыть отменить одну
из них или дождаться её. Тогда задача переживёт родительскую операцию и будет
писать в уже закрытые ресурсы.

Structured concurrency решает именно эту проблему: дочерние задачи живут внутри
лексического scope родителя. Родитель не может выйти из блока, пока дети не
завершились; отмена и ошибка распространяются по дереву; результаты и исключения
собираются в одном месте. Это не preview API в решении: используется обычный
`ExecutorService`, а structured concurrency только объясняется как следующий
шаг. Она не ускоряет вычисления и не заменяет deadline — она делает управление
временем жизни задач дисциплинированным.
