# Задание 4. Правильный executor

## Starvation при общей конфигурации

В первом сценарии два blocking I/O и две CPU-задачи делят пул из двух потоков.
Оба потока занимают I/O-задачи и ждут на latch. CPU-задачи уже лежат в очереди,
но запускать их некому: свободных потоков нет.

```text
shared fixed pool of 2:
  cpu tasks started while I/O holds both threads: false
  [shared-1] blocking task finished
  [shared-2] blocking task finished
  cpu tasks started after release: true
```

Это не перегрузка CPU. Процессор как раз свободен, но пул исчерпан: блокирующая
задача удерживает поток, пока ждёт ввод-вывод. Чем меньше пул и чем дольше
блокировки, тем вероятнее starvation. Тот же эффект возможен и без явной
блокировки: если задач больше, чем потоков, часть очереди ждёт.

## Разделение исполнителей

Во втором сценарии 100 блокирующих задач отправлены в
`Executors.newVirtualThreadPerTaskExecutor()`, а CPU-задачи — в отдельный
`newFixedThreadPool(availableProcessors())`. Пока виртуальные потоки ждут,
CPU-пул свободен и сразу начинает работу.

```text
separate executors:
  100 virtual I/O tasks waiting, cpu tasks started: true
  cpu total=5999994000000
```

Размеры выбраны по смыслу задач:

- **CPU-bound.** Поток почти всё время считает. Лишние потоки не ускоряют работу,
  а добавляют переключения контекста. Размер — число ядер процессора.
- **Blocking I/O.** Поток большую часть времени ждёт. Для platform threads размер
  должен покрывать ожидаемое число одновременных ожиданий (а не число ядер).
  Для virtual threads фиксированный размер не нужен: поток на задачу, а носителей
  (carrier threads) ровно столько, сколько нужно для CPU.

## Virtual threads

`newVirtualThreadPerTaskExecutor()` создаёт виртуальный поток на каждую задачу.
Когда такой поток упирается в блокирующий вызов, JVM снимает его с carrier-потока
(unmount), и carrier выполняет другие виртуальные потоки. Поэтому тысячи
ожидающих задач стоят несколько platform threads, а не тысячи.

Это повышает **масштабируемость ожидания**, но не ускоряет CPU-bound код:
виртуальные потоки не добавляют ядер и не делают вычисления параллельнее.
Для CPU-bound задач по-прежнему нужен пул размером с число ядер. Виртуальные
потоки также не помогают, если блокировка удерживает монитор или выполняется
нативная операция, которая не умеет размонтироваться.

Код остаётся прямым: обычные `submit`, `Future.get`, `try/finally` и обработка
исключений. Не нужны ни колбэки, ни ручное управление колбэками
`CompletableFuture`.

## Завершение

Оба executor'а освобождаются в `finally`: `shutdown`, ограниченное
`awaitTermination`, при неудаче — `shutdownNow` и ещё одно ожидание. Latch
`release` открывается в `finally`, поэтому блокирующие задачи не могут остаться
навсегда.
